# 发布之后的长期负担

发布不是终点。**真正拖垮一个项目的是发布之后那些重复发生、又没人愿意做的事。**
本篇把它们列全，并给出一个可操作的分类：哪些必须一次性做掉、哪些必须交给机器、
哪些永远无法自动化。

## 一、先给「痛」分两个坐标

两个轴决定处置方式，**先分类再动手**：

| | **机器可判定** | **必须人类判断** |
|---|---|---|
| **一次性成本** | 做完就永久生效 ⇒ **花一次时间配好** | 只能靠**降低触发频率** |
| **持续成本** | ⇒ **必须进流水线，定期跑** | ⇒ 只能靠**政策与预期管理** |

**判据**：凡是落在「机器可判定」那一列里的，**一律不允许靠人记住**。
人一定会漏，而漏掉的代价通常在半年后才出现 —— 那时已经没人记得当初为什么该做。

### 一条反直觉的：枯燥 ≠ 低回报

「枯燥、回报低」是最常见的误判。真实情况是三件事叠在一起：

- **回报延迟**：这些事防的是灾难，没出事就看不见回报；
- **回报分散**：省下的时间摊在很多天里，单看每天都不值一提；
- **代价集中**：一旦漏掉，代价一次性砸在一个具体的人头上。

⇒ 所以判据不该是「这件事有没有意思」，而是**「它能不能变成流水线里的一步」**。
能变成一步的，一口气做掉，以后再也不用想；不能的，才需要政策。

## 二、一次性成本：现在花半小时，省下几年

| 问题 | 症状 | 一次性动作 | 现成的东西 |
|---|---|---|---|
| 发布凭据是长期令牌 | 令牌一旦被钓鱼 / 泄露，别人可以直接以你的名义发包 | 换成 **OIDC 信任发布**：不再存任何长期发布令牌 | 主流注册表**到 2025 年底已全部支持**这一模式；其中一个注册表上线两年多已有**逾百万次**经此上传 |
| Action 用可变标签 | `uses: foo/bar@v3` —— 标签可以被改指到别处，等于把执行权交给上游 | **固定到完整 SHA** | 专门的固定工具；依赖更新机器人也能把 SHA 一起升 |
| 工作流权限默认过宽 | 任何一个被入侵的第三方 Action 都顺带拿到写权限 | 顶层 `permissions: {}`，**权限逐 job 授予** | 平台官方安全加固指南 |
| 没有漏洞上报通道 | 白帽只能开公开 issue，漏洞先被公开 | `SECURITY.md` + 平台的**私密漏洞上报** | 平台内置 |
| 主干可以被直接推 | 一次误操作就改了主干，且无痕迹 | **规则集**：要求 PR、要求检查通过、要求签名提交 | 平台 Rulesets |
| 版本号靠手改 | 人一累就写错，而且事后无法验证对错 | 提交信息约定 + **自动推导**版本号 | conventional commits 体系（见第三节） |
| 变更记录靠手写 | 前三个版本认真写，第十个变成「若干修复」 | 自动生成 | 提交信息驱动的生成器；平台内置的按标签分组 |
| 制品无法被独立验证 | 用户只能「选择相信你」 | 生成**构建证明（attestation）** | 官方证明 Action（注意：旧名那个在 v4 起只是新包的**一层包装**，新项目直接用新包）；用平台的证明校验命令核验 |
| 首次贡献者能直接触发 CI | 恶意 PR 能在带密钥的上下文里执行 | 打开「**所有**外部贡献者都需批准」 | ⚠️ 只开「首次贡献者需批准」**不够** —— 攻击者可以先交一个无害的错字修复骗取信任 |
| 发布之间的依赖会腐坏 | 半年不动，再动就是一次大升级 | 让更新机器人在**无人值守**下保持贴近最新 | 见第三节 |

> 判据：**凡「配好之后就不需要再想」的，一律现在配。**
> 这一节里的每一项，事后补救的成本都是当初配置的十倍以上。

## 三、持续成本：必须交给机器

| 问题 | 为什么痛 | 现成的东西 | 关键配置 |
|---|---|---|---|
| 依赖更新洪水 | 20 个包开出 20 个 PR，评审队列被淹没；**队列一积压，自动更新就等于没开** | 依赖更新机器人 | **分组**是唯一最重要的设置：按生态分组、按类型分组；**安全相关的更新不分组**，让它们单独可见、单独排队 |
| 陈旧 issue / PR 堆积 | 队列变成一份「没人打算处理的承诺清单」，真正的新问题反而被淹没 | 官方的陈旧清理 Action（注意：早期那个独立 App **已废弃**，官方 README 明确指向 Action 版本） | 设定天数、**豁免标签**（安全、置顶之类）、**每小时执行上限**（平台的滥用防护会限流，不要指望一次跑完） |
| 多分支 backport | 每个修复都要手工挑选提交到 N 个维护分支，枯燥且极易漏 | 若干成熟的回移工具与其官方 Action | 用标签或注释触发，自动建 PR 并回帖；要求提交时带 `-x` 之类的溯源信息 |
| 依赖里混入有漏洞 / 许可证有问题的包 | 出问题才发现，追溯成本高 | PR 阶段的依赖审查 Action | 设为**必需检查**，否则它只是提示 |
| 安全姿势随时间腐坏 | 配置是「发布时对」，不是「永远对」 | OpenSSF **Scorecard**（官方项目，CLI + Action + API 三形态） | 它按约 18 项打分：分支保护、代码评审、危险工作流、令牌权限、依赖更新工具、依赖固定、签名发布、静态分析、安全策略、维护活跃度等 |
| 工作流自身有安全问题 | 模板注入、权限过大、危险触发器 | **两个工具分工**：一个查「能不能跑」（正确性），一个查「安不安全」（安全性） | 安全性那个支持 SARIF 输出，可接进平台的代码扫描；两者都该设为 PR 检查 |
| 上游刚发版就踩坑 | 新版当天就引入，等于拿生产环境当小白鼠 | **冷却期**：只采用发布已超过 N 天的版本 | 固定工具与依赖机器人都支持「最小发布年龄」这一项 |
| 自己写的自动回复制造噪声 | 机器人批量生成低质回复 / issue，把噪声放大 | —— 没有现成工具 | 加之前先问：**它会不会自己造噪声** |

## 四、机器能查的，绝不能靠人

下面这些应当各是一条命令，进流水线，定期跑。
**第二列是本仓库里真实存在的那条命令** —— 不是「应该做」，是「已经在跑」：

| 要查什么 | 对应的一条命令 |
|---|---|
| 版本号在**多处**是否同步（包清单 / 变更记录 / 徽章） | 结构自检脚本的版本一致性检查 |
| 行尾是否统一；每新增一种文本类型，是否在同一次改动里补了对应的行尾规则 | 结构自检脚本的行尾检查 |
| 有没有把编译缓存打进发布包 | 结构自检脚本的缓存检查 |
| **依赖是否已固定到不可变引用** | 工作流自检脚本 |
| **工作流权限是否已最小化** | 工作流自检脚本 |
| 是否含密钥形态的字符串 | 回验脚本的凭据残留复查 |
| 文档里的相对链接与锚点是否可达 | 结构自检脚本的链接检查 |
| 目录比对是否**分栏**报告（「各自独有」与「同名但内容不同」分开） | 回验脚本与发布物一致性检查里的比对函数 |

> 写这类检查时守一条元规则：**检查某种字面量的代码，自身不得含有该字面量的完整形态**
> （规则常量用字符串拼接构造），否则将来一次全局替换会把它改坏，而它仍然打印「通过」。

> 表里第 8 条是唯一一条**没有独立命令行入口**的 —— 它以函数形式落在脚本内部，
> 由别的检查调用。这不算不合格（它确实在跑），但要如实这样标注，
> 而不是把它算成「已经是一条命令了」。

## 五、永远无法自动化的那几件

以下三件事**不存在「配置好就不用管」的解法**：

1. **判断一次改动是否破坏兼容性。** 工具能覆盖一部分 —— 同语言生态里有专门工具，
   思路是比对两个版本**自动生成的公开 API 描述**，而不是直接读源码；
   实测显示这类问题比人们以为的常见得多。但**语义级破坏（类型没变、行为变了）永远查不出来**。
   ⇒ 能自动化的交给工具，剩下的靠版本号纪律兜底：**只要有破坏性改动，就升主版本**。
2. **决定要不要接受一个贡献。** 这是评审，不是校验。
3. **决定一个项目什么时候该停止维护。** 这个决定不能外包给任何机器人。

对这三件事，唯一有效的杠杆是**降低触发频率** —— 把问题在更早、更便宜的阶段拦住。

## 六、2026 年的新变量：贡献洪水

这是**目前对维护者冲击最大、且没有现成解法**的一类问题。

**规模**：平台上每月合并的 PR，从 2023 年初的约 2 500 万涨到 2026 年的 9 000 万以上；
其中由自动化代理提交的约占每月 1 700 万。多项 2026 年的研究给出同一个方向：
这类提交平均问题数明显高于人类提交（一项实测约为 **1.7 倍**），
且第一次人工评审后往往需要更长时间才能合并。

**已经发生的应对**（都可照抄）：

- 某被广泛依赖的网络库：2025 年只有不到 **5%** 的安全报告是真的，约 **20%** 属于
  「读起来很专业但里面什么都没有」⇒ **2026 年 1 月直接关掉了悬赏计划**。
- 某游戏引擎项目：待处理 PR 积到 **4 681** 个，维护者称之为「消耗且令人沮丧」。
- 某终端模拟器项目：要求**先开 issue 并被接受**才能提 PR；直接关闭「路过式 PR」；
  对反复提交低质内容的账号**永久封禁**。
- 某白板库项目：**直接关闭所有外部 PR**。

**可照抄的五条动作**（顺序很重要：**先政策，后工具**）：

1. **先写一份贡献政策**，把争论从每个 PR 的评论区搬到一处：要求**披露**是否用了 AI 辅助；
   责任必须由**人类**承担（不把 AI 列为共同作者、不让 AI 代为签署）；
   提交者必须能**解释自己提交的改动**。
2. **要求先开 issue 再提 PR** —— 把「要不要做」和「做得对不对」拆成两步。
3. **打开「所有外部贡献者都需批准」**（不只是首次贡献者）。
4. **用规则集把政策变成强制**（必需标签、必需检查），而不是靠友善提醒。
5. **保留「临时关闭外部 PR」这个开关** —— 它是最后一道闸。

> 反面教训同样值得抄：有项目发现，**自己用来管理 issue 的自动化脚本本身在批量生成低质 issue**，
> 外部贡献者又把这些描述喂给自己的工具生成 PR —— 自动化把噪声**放大**了而不是缩小了。
> ⇒ **任何自动回复 / 自动分类机制上线前，都要先确认它不会自己造噪声。**

**人的那一面**：维护者倦怠是可测量的 —— 多项调研里约 **46%** 的维护者有倦怠经历，
在热门项目里比例更高。它**不是个人心理问题**，而是「评审能力跟不上提交量」的结构问题。
自动化能救的部分，就是本篇前四节那些。

## 七、检查清单

**这张表有两列。第二列是这个仓库自己的现状 —— 写下来，让它变可见。**

为什么要写第二列：一份「应该做什么」的散文清单，最大的风险不是「漏做了」，
而是「漏做了而没人知道」—— 自检器全绿，清单一条条读过去也全对，
因为**没有任何东西在检查这份清单本身**。把现状写进表里，
至少让缺口在每一次阅读时都露一次面。

| # | 清单项 | 本仓库现状 |
|---|---|---|
| 1 | 发布凭据已换成 OIDC 信任发布 | **不适用**：本仓库不发布到任何包注册表，只用平台内置令牌建 Release |
| 2 | 所有第三方 Action 固定到完整 SHA，且明确「谁负责升级」 | **已做**：两个 Action 均固定到完整 SHA；升级由依赖更新配置负责；由工作流自检脚本守住 |
| 3 | 工作流顶层 `permissions: {}`，权限逐 job 授予 | **已做**：顶层为空映射，两个 job 各自声明；由工作流自检脚本守住 |
| 4 | 有安全策略文件，并开启了私密漏洞上报 | **部分**：安全策略文件已补；但「私密漏洞上报」是**平台侧开关**，仓库内无法核验 —— 要去网页上确认 |
| 5 | 有规则集保护主干：要求 PR、要求检查通过 | **无法核验**：平台侧设置 |
| 6 | 「**所有**外部贡献者都需批准」已打开 | **无法核验**：平台侧设置 |
| 7 | 版本号与变更记录由提交信息自动推导，不靠手改 | **未做**：变更记录仍逐条手写 |
| 8 | 依赖更新已配置**分组**，且安全更新**不**分组 | **已做**：常规更新按类型分组并设了冷却期；安全更新走平台独立通道，不写分组规则即默认不分组 |
| 9 | 陈旧 issue 有自动处理，含豁免标签与每小时执行上限 | **未做** |
| 10 | 处理低质贡献的政策写在一眼能找到的地方 | **已做**：贡献指南里有「低质贡献与 AI 辅助」一节 |
| 11 | 自动回复 / 自动分类机制经过一次「它会不会自己造噪声」的复核 | **不适用**：本仓库没有机器人 |
| 12 | 「机器能查」的那份清单，每一条都真的是一条命令 | **部分**：8 条里 7 条有独立命令入口，第 8 条以函数形式落在脚本内部（见第四节） |

小计：**已做 4、部分 2、未做 2、不适用 2、无法核验 2**（合计 12）。

> **「无法核验」不是「通过」。** 这两项要么去平台设置里确认，要么就让它一直标着
> 「无法从仓库核验」—— 把它写成「已做」是自欺，写在「已做」里也让下一个人失去警觉。
>
> **「未做」的两项也一样有价值**：它们现在是已知的、写在表里的缺口，
> 而不是「读起来处处都做到了」的错觉。
