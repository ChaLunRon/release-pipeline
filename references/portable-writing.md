## 一、为什么要做这件事

一份技能 / 文档会在多台机器、多个网络上被使用。**把「某一台机器在某一时刻的样子」
写成「这个平台的属性」，换一台机器就变成误导** —— 而且这类错误的伪装性极强：
它读起来像一句技术事实，没人会去核对，于是可以存活很久。

最典型的两种：

1. **把环境快照写成能力边界。** 「读不到」「不可用」这类结论，其实只对当时那台机器、
   那个网络出口成立。读者看到会推出一句从未被验证的结论：「那我这台也一样」。
2. **把具体取值当常量。** 地址段、端口、绝对路径、某个工具的存在与否 ——
   这些在另一台机器上大概率不同，写进文档就把「方法」降级成了「传闻」。

**判据一句话：留「怎么判、怎么修、怎么验」，删「我这边是什么样」。**

## 二、三类内容，处置方式完全不同

| 类别 | 特征 | 处置 |
|---|---|---|
| **普适** | 方法、判据、命令、失败特征、规范约束 | ✅ 保留，并且**写成能照着做的步骤** |
| **环境专属值** | 绝对路径、IP 段、端口、hosts 指向、某工具是否安装、某次查询结果 | ❌ 删除，**改写为「如何探测出该值」** |
| **示例** | 面向使用者的话术、示例地址、示例文件名 | ✅ 保留 —— 它不是断言，而是示范 |

**第三类最容易被误删。** 两个「看起来像第一人称」但其实是正确的例外：

- **面向使用者的话术**（技能对用户说的话）—— 用第二人称是对的。
- **确实在指「使用者/读者的机器」的句子** —— 例如安装提示里的
  「如果你的机器不允许全局安装」。这里的「你的机器」有明确先行词。

要删的是**没有先行词的第一人称环境指代**——那类把作者所在环境与读者所在环境混为一谈的写法。
被禁词表（「本机」「我这台机器」「实测环境」等）定义在 `scripts/selfcheck.py` 的 `ENV_REFERENCE_WORDS`：<!-- portability-exempt: 这一句必须举出被禁写法，否则读者无从下手 -->
它们出现在公开文档里时没有先行词，读者只能理解成**自己那台**，
于是把作者的观测误当成自己的处境。

## 三、改写对照表

| 类别 | ❌ 不要写 | ✅ 改成 |
|---|---|---|
| 绝对路径 | 某个具体的用户目录路径 | 用环境变量或占位：`$HOME` / `%USERPROFILE%` / `<你的用户目录>` |
| 客户端的安装位置 | 某个具体安装路径 | 「客户端自带的 CA 包（路径随安装方式而变，用 `git config --show-origin` 查）」 |
| 地址段 | 某个具体的 IP 地址或网段 | 「查服务方公布的网段（如 `api.github.com/meta`），**现查**」 |
| 代理端口 | 某个具体端口号 | 「查系统代理设置与环境变量」，而不是猜端口 |
| 出口有没有代理 | 「这台机器有代理」 | 「**先判定出口形态**：直连 / 系统代理 / 本地中间人，三种解法不同」 |
| 某个工具 | 「装了某某加速器」 | 「**若**存在本地中间人（加速器类工具常见做法：改 hosts 指向回环 + 回环端口做中间人），则……」 |
| 命令是否存在 | 「这台机器没有 `gh`」 | 「**先检测再分支**：`command -v gh` 有则用之，无则走令牌方式」 |
| 系统差异 | 「Windows 上必须……」 | 把平台差异写成**并列分支**，而不是把作者所在平台的结论当通例 |
| 报错原文 | 报错里夹带的具体地址 | 保留报错文本、**脱敏**其中的地址与标识 |
| 一次性观测 | 「某个接口返回 502」 | 「（<年-月> 实测，此环境下）某个接口返回 502」—— 带上时间与条件 |

**最后一行是全篇最重要的习惯**：观测不是不能写，而是**必须带上「什么时候、什么条件下」**，
让读者知道它的适用范围。**把单环境快照当平台属性**，才是问题。

## 四、实测结论的正确写法

同一个事实，两种写法差在**读者能不能复现与核对**：

| 方面 | 差的写法 | 好的写法 |
|---|---|---|
| 时间 | 无 | 「（<年-月> 实测）」 |
| 条件 | 无 | 「在<某种出口形态>下」「走<某种后端>时」 |
| 证据 | 「不可用」 | 给出可核对的锚点：状态码、错误字符串、命令与它的输出 |
| 适用范围 | 隐式当成平台通用 | 明说「这是<某个网络>在<某个时刻>的情况，换环境请按本文方法重新判定」 |

另外一条容易被忽略的：**同一个文件内部要自洽**。
如果「已知限制」一节写着「结论是实测时点的情况」，正文却写成绝对的「不可用」，
那就是自打脸 —— 这类矛盾正是读者最先发现的那一种。

## 五、把可移植性做成机器判据

**光靠自觉会反弹。** 把它变成自检器里能判的规则，每条改动都要过这一关。
本仓库的 `scripts/selfcheck.py` 实现三条（命名与阈值以该脚本为准）：

| 规则 | 级别 | 判据 |
|---|---|---|
| 硬编码的绝对路径 | **FAIL** | 文档与配置里出现「盘符 + 反斜杠」路径，或『`/Users/<用户名>`、`/home/<用户名>`』形态的绝对路径 |
| 地址字面量 | **FAIL** | 任何文件里出现 IPv4 字面量，且**不在白名单**（回环地址 + 文档保留段） |
| 第一人称环境指代 | **WARN** | 文档里出现被禁的词表；**同一行含豁免标记则跳过** |

三条设计要点：

1. **规则常量用「字符串拼接」构造**，不要写成完整字面量 ——
   否则将来做一次全局替换（改名、换署名）会把检查器自己一起改坏，
   而它**会静默失效**：检查照样「通过」，只是再也查不出东西。
   **通用规则：任何「检查某种字面量」的代码，都不得含有该字面量的完整形态。**
2. **测试夹具同理**：测试需要造出违规样例，那就用拼接构造夹具字符串
   （例如把盘符、分隔符、用户名分段拼起来），这样夹具不会把自己的仓库判成违规。
3. **豁免标记要可清点。** 允许极少数「必须举例说明被禁写法」的行带豁免标记，
   但自检器要**把标记数量打印出来**。数量一旦上涨，说明有人在拿它绕过检查。
   **豁免必须是显式的、可数的，而不是静默的。**

## 六、换机器后的复检动作

- [ ] 全仓库搜一遍硬编码的绝对路径与地址字面量（自检器规则一、二）。
- [ ] 搜第一人称环境指代（规则三），**逐条分类**：该改 / 属上文两个例外之一。
- [ ] 凡是「实测」「不可用」「读不到」的句子，检查是否带了**时间与条件**。
- [ ] 凡是「先决条件」类描述（装了某命令、有某工具），检查是否写成了**检测 + 分支**，
      而不是假定它存在。
- [ ] 跑一次自检器，确认豁免标记的数量**没有增长**。
- [ ] **把仓库整体复制到另一个路径下再跑一次自检与全部测试** ——
      这是唯一能证明「没有隐含依赖当前路径」的动作。
