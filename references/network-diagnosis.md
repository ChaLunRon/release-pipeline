# 网络通路分层诊断

换一台机器、换一个网络，第一件要确定的事是：**到 GitHub 的通路卡在哪一层。**
本文给的是一套**分层判据**，每一层都能独立被证伪；不要一上来就写重试脚本或换工具。

## 一、先跑一次通用探针

```bash
git ls-remote <仓库URL> HEAD
```

- **返回 40 位 sha** ⇒ DNS、TCP、TLS 全通，且**读权限**也通
  （公开仓库这一条**不需要认证**）。可以直接进入推送环节。
- **报 `could not read Username`** ⇒ TLS 已通过，只差凭据 —— 这是**好消息**，
  转去处理令牌与凭据。
- **报 TLS / 连接类错误** ⇒ 继续往下分层。

⚠️ **两条容易误用这个探针的地方**：

1. **`ls-remote` 通 ≠ 凭据可用。** 它对公开仓库免认证，所以「远端能读到」和
   「我能推上去」是两件事。曾经据此误判过「网络没问题，那大概推成功了」。
2. **网络类命令要在无沙箱模式下跑。** 执行环境若带沙箱或代理，出口可能被改道，
   让 `curl` 拿到占位 `200` 或 `502`。**以 `git ls-remote` 为准，不以 `curl` 为准。**

## 二、五层定位法

从下往上逐层证伪，**某层通过就不再怀疑它下面的层**。每层都给出判据与常见根因。

### 第 1 层 · DNS

```bash
python -c "import socket;print(socket.getaddrinfo('<域名>',443))"
```

**判据不是「解析出没解析出来」，而是「解析到的地址是否属于该服务自己公布的网段」。**
权威依据是 `api.github.com/meta`（**现查，别背**）—— 它列出 GitHub 各服务的官方网段。
解析结果落在该服务之外的地址段，说明 DNS 被改写了。

- 常见根因：本地 DNS 被投毒 / 被运营商改写 / 用了被劫持的公共 DNS。
- 交叉验证：换一个解析来源再查一次。**若两个来源给出同样的错误地址，那说明改写在更上游**，
  这条路就不必再走（曾经踩过：换公共 DNS 复核，结果拿到同样被污染的地址）。

### 第 2 层 · TCP

```bash
python -c "import socket;s=socket.socket();print(s.connect_ex(('<边缘IP>',443)))"
```

**判据**：返回 `0` = TCP 通；非 0 = 连不上。
区分「连不上」与「连上但立刻被切断」—— 后者说明问题在更上层（TLS / SNI）。

### 第 3 层 · TLS 与 SNI

同一个边缘 IP，**分别带域名与不带域名**做一次握手：

```python
import socket, ssl
ctx = ssl.create_default_context()
for sni in ("<域名>", None):
    try:
        raw = socket.create_connection(("<边缘IP>", 443), timeout=8)
        ctx.wrap_socket(raw, server_hostname=sni)
        print(sni, "OK")
    except Exception as exc:
        print(sni, type(exc).__name__, exc)
```

**判据**：**带域名被重置、不带域名成功 ⇒ 阻断发生在 SNI 层。**
（域名根本没发出去，中间设备就无从按域名拦截。）
如果两者都失败，问题在 TCP 或更下面。

### 第 4 层 · HTTP

用真实 IP + 手工 `Host:` 头请求一次，看状态码是否正常。
这一层能区分「TLS 通了但服务异常」与「TLS 根本没通」。

### 第 5 层 · 认证

走到这一层才轮到令牌与凭据。**症状**：`fatal: could not read Username`、
`Authentication failed`、`refusing to allow a Personal Access Token…`。
处理方式见令牌与凭据一篇。

## 三、判定 SNI 层阻断的正确姿势（与它的诚实边界）

当需要绕过 SNI 做**只读**诊断时，可以建一条**不发 SNI**的连接：

```python
raw = socket.create_connection(("<真实IP>", 443), timeout=8)
tls = ctx.wrap_socket(raw, server_hostname=None)   # 不发 SNI
tls.sendall(b"GET /repos/<owner>/<repo> HTTP/1.1\r\nHost: api.github.com\r\n"
            b"User-Agent: diag\r\nConnection: close\r\n\r\n")
```

- **认证不能省**：`check_hostname=False` 可以，但 **`verify_mode` 必须是 `CERT_REQUIRED`**
  （证书链仍要校验，再取 SAN 手工核对）。把 `verify_mode` 也关掉，就等于对中间人完全不设防。
- **诚实边界**：不发 SNI 时，服务方的边缘节点会回落成通配符证书，
  而**通配符不覆盖 `api.<域名>` 这种子域**。因此这条连接只能证明
  「对端确实是该服务方、中间人已排除」，**不能**说成「主机名已核对」。
  措辞上要守住这条线。
- 取 SAN 时若某个可选依赖缺失，**换成标准库实现，而不是降级为空字符串**。
  曾经犯过这个错：脚本在依赖缺失时返回了字面量「未能解析」，
  等于 SAN 检查**根本没执行**，而结论已经被写成「安全未降级」。
  **凡是「已验证 X」的措辞，都要能指回具体哪一行证明了 X。**

## 四、三类环境的解法

### A. 直连可用

不做任何证书配置。这是最省事也最不容易出错的一类。

### B. 需要 HTTP(S) 代理

```bash
git config --global http.proxy <代理URL>      # 或
export HTTPS_PROXY=<代理URL>
```

- **用 `--noproxy '*'` 做对照**，确认差异确实来自代理。
- 有的客户端在系统信任库里会走**吊销检查（CRL/OCSP）**，而某些出口到这步不可达 →
  表现为「证书吊销功能无法检查」。**这不是证书坏了**，换用不默认做该检查的 TLS 后端即可。
- 平台间的差异要注意：同一台机器上不同工具可能用**不同的 TLS 后端**，
  所以**别用 A 工具的报错去判断 B 工具的配置**。

### C. 本地存在中间人加速器

这类工具通常做两件事：改写系统 hosts 把目标域名指向**回环地址**，
再在回环端口上做 **TLS 中间人**转发。于是 git 会同时撞上两条互斥报错：

| 后端 | 报错 | 原因 |
|---|---|---|
| 系统信任库后端 | 吊销检查不可达 | 信任中间人证书，但吊销查询出不去 |
| OpenSSL + 默认 CA 包 | `unable to get local issuer certificate` | **不认**中间人的根证书 |

**干净修法（全程不关闭证书校验）：把中间人的根证书显式加进信任链。**

```bash
# 1) 导出中间人根证书（Windows 用 certutil，macOS 用 security，Linux 视工具而定）
#    证书在系统「受信任的根证书颁发机构」存储里
# 2) 转成 PEM
# 3) 与客户端自带的 CA 包**拼接**（顺序：自带的在前，中间人根在后）
cat "<客户端自带的 ca-bundle>" <中间人根.pem> > "<合并后的 ca-bundle>"
# 4) 告知 git 使用合并后的包，并换用不默认做吊销检查的后端
git config --global http.sslBackend openssl
git config --global http.sslCAInfo "<合并后的 ca-bundle>"
```

- **不要用「关闭吊销检查」当解法**：该开关在部分 Git for Windows 版本上实测**无效**
  （设了照报），既降级又不解决问题。
- **`curl` 在 Windows 上走的是另一个 TLS 后端，会忽略 `--cacert`。**
  所以**别用 `curl` 判断 git 的证书配置是否生效**；
  **以 `git ls-remote` 为准：它返回 `fatal: could not read Username` 就说明 TLS 已通过、只差凭据。**

### D. 三类都不行

换一条通道，并**如实说明代价**：

- 远程连接器类通道**通常只能按「写文件」方式推送**（没有建 tag 的能力，
  提交时间也会变成当前时间）⇒「N 个 tag ↔ N 个归档快照逐文件一致」这条保证守不住。
  使用者在意历史时，必须把这个代价讲清楚，别默认走这条路。
- 或者把命令交给使用者在自己的终端里执行 —— 凭据完全由他掌控，最稳。

## 五、不要做的事

- ❌ **不要把证书校验整个关掉。** 正确做法是把中间人根证书加进信任链。
- ❌ **不要把某一次探测到的 IP / 端口 / hosts 指向写进公开文档。**
  那是**某个网络在某个时刻的状态**，换一台机器就是错的信息（详见可移植写法一篇）。
- ❌ **不要用另一个 TLS 后端的报错判断当前配置。**
- ❌ **不要靠猜端口来找代理** —— 查系统代理设置与环境变量，比扫端口可靠也礼貌。

## 六、换机器后的复检清单

- [ ] `git ls-remote <仓库URL> HEAD` 能返回 sha 吗？
- [ ] 若失败：DNS 解析结果是否属于该服务公布的网段（`api.github.com/meta` 现查）？
- [ ] 若 TCP 通但 TLS 挂：带域名与不带域名的握手结果是否**不同**（⇒ SNI 层）？
- [ ] 若走代理：加 `--noproxy '*'` 后的差异说明什么？
- [ ] 若走中间人：根证书**是否真的加进了信任链**（而不是关了校验）？
- [ ] 结论里有没有把「这次探测的地址」当成「这个服务的地址」写下来？
