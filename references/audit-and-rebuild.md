# 快照号位取证与仓库重建

**只在这一种输入下需要**：手里是一堆并列的版本快照（文件夹或 zip），
而它们的号位来自「第几个保存的」，跟内容对不上。

> 正文主文件里的「阶段 1」给了这件事的骨架；本文是操作细节。
> 若手里已经是一个历史线性的 git 仓库，**直接跳过本文**。

## 一、先盘点，建立基线

列出包内每个版本子目录的文件数、体积、各文件哈希。**后面所有结论都要能回溯到这一步的基线。**

一条纪律贯穿全文：**只读用户既有资产。** 旧包、旧 zip 一律不删不改，
新产出**另起文件夹**，旧件的修改时间保持不变（交付后回查一次，用来自证只读）。

## 二、号位取证：三路证据

对相邻快照做三重复核，**三路证据一致才下结论**：

| 证据 | 做法 | 能回答什么 |
|---|---|---|
| 文件集合 | 比 `same` / `added` / `removed` / `changed` 计数 | 谁是谁的后继 |
| 特征串探针 | 在正文里搜只有某一版才有的字符串 | 内容属于哪个开发阶段 |
| 相似度 | 行级 `difflib.SequenceMatcher` 的 ratio | 分支点在哪 |

单靠相似度会误判。实测过这么一组：两个快照的行级相似度 **0.968**，
看着像「差一点点」，其实它们是**同一开发阶段的前后两步**，都不是大版本。
反过来，某个快照与「更晚的那个正式版」高度相似，说明它是**那个正式版的开发中期态**，
号位要往**下**修正。

⚠️ **判定标准必须始终一致。** 实测出过自相矛盾：与正式版相似度 0.968 的被降为次版本，
而 **0.9875 的反被升成大版本** —— 只因为「它是第 8 个保存的快照」。
用同一把尺子量所有快照，是这一节唯一不能妥协的地方。

**顺手检查号位序列有没有空洞** —— 有空洞通常就是错标的信号（例如 5.0 之后直接跳到 8.0）。

## 三、改号位只动标签维度

**改号位 ≠ 改内容。** 只动：

- 包清单里的 `name` 字段与正文标题里的版本串；
- 明确标出版本号的元数据；
- 每处改动附一份 `RELABEL-NOTE.md` / `RENUMBER-NOTE.md` 说明原因。

**正文内容一个字都不动。** 动了就破坏了「号位 ↔ 内容」的对应关系。

**作废的号位不复用。** 若某号位曾被错误占用，就正式宣布它作废
（写进 CHANGELOG 与 README），**而不是把后来的内容挪上去** ——
否则所有指向旧号位的引用都会静默地指向另一份内容。

> **别在最终产出目录上原地改。** 暂存放临时目录、从只读源重建，
> 最后一步才写进产出目录；所有人工改动写成脚本里的显式 `(old, new)` 补丁表。
> 否则脚本重跑一次就会把成果覆盖掉。

## 四、从并列文件夹到 tag 历史

**用 git tag 表达版本历史，不要用并列文件夹。** 并列文件夹会让平台上出现 N 份重复副本，
而且包清单不在仓库根就装不上。

```
git init -b main
# 每个版本：清空工作区 → 拷入该版内容 → git add -A → 带 GIT_AUTHOR_DATE 提交 → 打 tag
```

- 提交时间戳按**当时真实开发日期**回填，并在 README 里**明确披露**是事后重建的。
- 每个 tag 与归档快照**逐文件核对一致**后才算完成。
- **仓库根目录名必须等于包清单里的 `name`。** 别用 `repo/` 这类通用名当仓库根 —— 会直接装不上。
- 脚本里对每个仓库写一遍 `git config user.name` / `user.email`，日期用环境变量**内联**传入；
  只靠环境变量而不写仓库级身份，事后手工 `amend` 会报 `Committer identity unknown`。

⚠️ **提交前删掉 `.git/index` 强制重哈希。** 重建历史时相邻两版的某个文件经常
**体积完全相同**（只有一行版本号不同），而复制文件时若保留了修改时间，
`git add -A` 会**命中 stat cache 而不重新哈希**，把上一版的内容留在新版提交里 ——
而 `git status` 还显示「干净」。
复制文件用「复制 + 显式设置时间」，不要用会保留原时间的便捷函数。

## 五、填实名：标识符与说明性句子是两回事

把占位值换成真实身份时，**先分清两类**：

| 类别 | 例子 | 处置 |
|---|---|---|
| **纯标识符** | URL 里的 owner、署名元数据、邮箱、别名 | 可以**机械替换** |
| **说明性句子** | 「发布前把 X 换成真名」「忘了替换 X 会 404」 | **必须手工改**，否则语义错乱（变成「忘了替换 某某」） |

实测 32 处命中里，**12 处必须手工改**。做法：

1. 先导出「逐行列出命中行 + 上下文」的清单；
2. 再分**显式补丁表（改语义）**与**机械规则（纯标识符）**两段执行；
3. 每步断言「恰好匹配一次」；
4. 最后逐行复核残留。

⚠️ **已归档的历史快照与旧 tag 不要改。** 填实名只改**当前版本**。
归档里的旧署名是**事实记录** —— 改了会破坏「tag ↔ 归档快照逐文件一致」这条可验证保证，
也等于伪造历史。要动先问使用者。

⚠️ **不要为占位符专门造工具。** 署名 / URL 里的 owner / 邮箱共用一个占位值，
发布前一次性替换即可。为它配「专用替换脚本 + 自检器『owner 必须 ASCII』规则」属于过度工程。
自检器留一条**只报警不失败**的「占位值清点」（数出还剩多少处）就够。

⚠️ **若要用 `git filter-branch` 改历史里的作者身份，它要求工作区干净** ——
有未提交改动会直接报 `Cannot rewrite branches: You have unstaged changes`。
正确顺序是：**先提交 → 再 filter-branch → 最后再改内容**。
跑完记得清 `refs/original/`、`reflog expire --expire=now --all`、`gc --prune=now`。
**不显式 export 提交日期变量，就会沿用原始提交日期** —— 重建历史时要的正是这个行为。

## 六、逐条复核外部评价

**逐条给出机器验证结果**，分三类输出：

- **成立**（附证据；能精确到字节最好）
- **需精确化**（方向对，措辞不准 —— 给出更准确的说法）
- **不成立 / 不公平**（说明为什么，但仍然吸收其中的合理关切，给出替代方案）

两条纪律：不要笼统说「总体合理」；不要因为评价来自外部就默认它对。
另外**主动报告评价漏掉的问题** —— 一份只复述评价的复核没有增量价值。

## 七、交付包的文档层体检

代码与 git 都过了，**文档层仍可能被人一眼看出不对**。

### 三条写作纪律

1. **不得出现没有先行词的第一人称环境指代。**
   它们在公开文档里没有先行词，读者只能理解成自己那台；
   而同一个仓库里往往另有把这类词用于**读者机器**的句子 —— 语义直接撞车。
2. **实测结论必须写成「带日期 + 可核对的条件」**：给出时间、环境形态、可核对的锚点
   （状态码、错误串、命令与输出），并说明适用范围。
   **把单环境快照写成平台属性**，才是问题。
3. **例外要分清，别一起改掉**：面向使用者的话术、以及确实指**使用者机器**的句子，
   保留原有语态才是对的。

### 累计型文件会静默被截断

`CHANGELOG.md` 这类「只增」的文件可能在某次重构里被整体砍掉几段，只留一个**空标题**，
而文件开头的内部指针还写着「完整证据见「X」一节」—— **指针指向空节**。

四步体检：① 找空标题 / 无内容的节（末尾那节最容易被忽略）；
② 检查每处「见 X 节」指向的节是否真的存在；
③ 核对上层文档对它的**覆盖声明**是否属实；
④ 定位是哪一步砍的 —— 逐版比行数，再从**内容正确的那个 tag** 恢复。

### 版本号升级：逐条显式替换 + 残留复核

**禁止全局盲替换。**

1. 先导出「全仓库命中行 + 行号」清单，**逐条判定**「当前版本语义 → 改」还是「历史引用 → 留」；
2. 脚本里每一步 `assert 命中数`（写错期望值时立刻炸，不要静默少改）；
3. 改完**打印全仓库残留逐行**复核。**合法残留只有 4 类**：
   变更记录的历史段、上层文档里的旧 tag 行、文档中「反例 / 示意」的举例、
   以及**已顺延的示例**（`2.0 → 2.1` 这类示例自身也要顺延成 `2.1 → 2.2`）；
4. **别忘不显眼的元数据**：引用文件的 `version` **与 `date-released`**
   （它常几个版本都不跟着 `version` 走）、包清单里的版本号、徽章里的版本串、
   `name` 与目录名。

**号位判断**：在**已发布**产物上做的内容修正 = **顺延新号位**，即使文件数少、也没动 `name`
—— 已推送的那个 tag 必须**一字节未动**。

### 改「结论类措辞」时要搜同义表达的全集

一条错误结论**改了两轮才改干净**：第一轮只搜了自己记得的那个词（「平台无关」），
改掉变更记录里的一处就以为完事；第二轮把「**逐字节 / 平台无关 / 跨平台 / 可重现 / 内容一致**」
几个词**一起**搜，才发现还有一份配置文件里写着「使发布物**跨平台逐字节可重现**」。

做法：① 先列出该结论的**全部可能措辞**（含近义与反义），一次性搜全仓库；
② 搜到之后**逐条判**是「同义的不准确」还是「本来说的就对」——
本次发布工作流里「因此与平台无关」指的是**指纹比对方法**，那一处准确，**不动**。

**别把「搜得全」和「改得多」混为一谈。**

## 八、复制与重建时的三个操作陷阱

三个都实测踩过，共同特征是**报错或现象指向错误的方向**。

### 陷阱 1：命令的工作目录，不是你以为的那个工作目录

两条实测踩到的形态，共同点是**不报错、只是把东西放错了地方**：

```
cp -r A B                       # B 不存在 → B 就是 A 的副本
cp -r A B                       # B 已存在 → 变成 B/A ！多出一层嵌套
git -C <目录> archive -o out.zip  # out.zip 落在 <目录> 里，不在你的 shell 目录里
```

第一形态实测把产出目录的文件数从 22 变成 110，**而源目录是干净的** ——
第一反应会去怀疑源被污染了。
第二形态实测让「检查产物大小」的语句报「文件不存在」，而产物其实已经生成，
只是落在另一个目录里。

**两条做法**：

- 复制用「源目录 + `/.`」的写法明确表达「把里面的内容放进目标」，
  或先确保目标不存在再复制；**复制完立刻数文件数，与源对比**。
- 跨目录执行命令时，凡带输出 / 输入路径的参数，**一律写绝对路径**，
  不要依赖「相对谁」的推断。

另外两条同族的执行方式陷阱：

- **路径里含 shell 特殊字符时要先落成脚本文件再执行**，不要内联 —— 特殊字符会被展开。
  同理，**内联执行时取自身所在路径的变量是未定义的**，只有落成文件才有意义。
- **先探测再分支，不要假定某个命令存在**：保底链路是「把结果写进文件 → 再读回来」。
  同一条链路在不同会话里可能时好时坏，所以**每次都要带保底**，不能依赖「上次它是好的」。

### 陷阱 2：目录改名被拒绝时，先怀疑句柄、别怀疑权限

按下纪律要把仓库目录改名成本名时，可能撞上「拒绝访问」。**先按「句柄 / 当前目录锁」排查**：

| 探测 | 结论 |
|---|---|
| 里面**每一个**子项都能改名 | 不是权限 / 属性问题 |
| **目录本身**、以及包含它的上层目录不能改名 | 某进程持有该目录 |
| 属性查询显示是目录，无只读标记、无重解析点 | 排除属性因素 |

在非提升态下看不到系统进程持有的句柄，找句柄的工具也可能被安全策略直接拦掉。
**不要在这上面耗时间**，改用复制方式重建：新建新名目录 → 复制内容（含 `.git`）→
逐文件哈希校验零差异 → 用 `git log` / 提交数 / `HEAD^{tree} == 旧tag^{tree}` 自证完整性。

**反直觉但实测成立**：同样的锁**挡得住改名，却挡不住删除**。
所以「删不掉」不要从「改不了名」直接推：

- **清理临时产出与旧交付物，走系统的回收站机制（可撤销），不要永久删除** ——
  清理脚本写到系统的临时目录并自删，不要污染项目目录。
- 换机器后回收站机制各不相同（桌面系统各有接口，类 Unix 用命令行封装），
  所以这里写的是**意图**（可撤销），不是某一条命令。

### 陷阱 3：比对 git 对象字节时不要用「文本模式 + 去空白」

用文本模式取下 git 命令的输出再 `.strip()`，会删掉尾换行 ⇒
**「全部文件都不一致」的假警报**（实测一次报出 120/120 全红）。
**用二进制模式取原始字节再算哈希。**

同类的一条：**过滤 `.git` 必须按路径分段比对**（判断路径的每一段是否恰好等于 `.git`）。
用子串判断会**连 `.github/` 一起排除**，文件数统计偏小。

## 九、检查清单

- [ ] 旧资产未被修改（修改时间未变，可自证只读）
- [ ] 号位序列连续，没有空洞
- [ ] 每个快照的真实版本号有指纹证据，且**判定标准前后一致**
- [ ] 改号位未动正文；每处有说明文件
- [ ] 作废号位已写进 CHANGELOG 与 README
- [ ] 仓库根目录名 == 包名 == 发布物文件名 == 目录名
- [ ] 提交前删过 `.git/index`；每个 tag 与归档快照**实际字节**逐文件一致
- [ ] 归档快照与旧 tag 仍是原样（归档冻结）
- [ ] 改实名的说明性句子逐句复核过
- [ ] 复制产出目录后数过文件数，与源一致（防 `cp` 嵌套）
- [ ] 版本号残留逐行复核过，剩下的都属于那 4 类合法残留
- [ ] 产出目录无编译缓存；磁盘实际文件数 == 受控文件数
