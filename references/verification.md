# 推送后的九项回验

**「本地全绿」不等于「线上正确」。** 每一次线上写操作之后，逐项回验才算做完。

可直接执行：`python scripts/verify_publish.py --owner <owner> --repo <repo> --local <本地仓库> --tag <tag>`

## 一、九项逐条口径

| # | 检查项 | 取数方式 | 判据 | 失败意味着 |
|---|---|---|---|---|
| 1 | 远端 `main` = 本地 `HEAD` = 本地新 tag | `git ls-remote` + `git rev-parse` | 三者 sha 相同 | 推送没走完，或推错了 ref |
| 2 | tag 名集合（远端 vs 本地） | 两侧列名取集合，**远端侧先剥掉解引用后缀** | **对称差为空** | 有 tag 没推上去，或推了个本地的野 tag |
| 3 | 全部**旧** tag 的 sha | 与推送前记录的基线比 | **零变动** | 历史被动过（强推 / 重建），必须立刻查 |
| 4 | 远端 `main` 树 vs 本地 **`HEAD` 树** | `GET /git/trees/<sha>?recursive=1` vs `git ls-tree -r HEAD` | 逐文件 blob 指纹，差异 0 | 推送的不是你以为的那个提交（**工作区有没有未提交改动，不影响这一项**） |
| 5 | 远端新 tag 树 vs 本地同名 tag 树 | 同上，两侧都取 tag 的树 | 差异 0 | tag 指向被改过 |
| 6 | 远端每个 tag 树 vs 本地归档目录 | 树的 blob 指纹 vs 归档目录逐文件指纹 | 逐一一致 | 归档快照与 tag 不符（归档损坏或被改过） |
| 7 | 全部 tag 本地树 vs 远端树 | `git ls-tree -r` vs API 树 | 逐一一致 | 某一版内容在传输中出问题（极罕见，但必须排除） |
| 8 | CI **本次提交**的 run | 按 `head_sha` 取本次提交的运行记录（服务端参数 + 本地再过滤一遍），再按 `created_at` 取最后一条 | `conclusion == success` | 校验失败，或这次提交根本没触发 |
| 9 | Release 资产 | 按**期望文件名**匹配 + 下载 + 与 tag 做逐文件内容比对 | 条目集合一致、**逐条目内容指纹**一致 | 发布物与 tag 不符（比第 5 项更严重：对外发错了包） |

**另有两项「附带判定」**，它们不单独算一项，但同样会被报告 ——
少了它们，前九项全绿也可能得出一个错的结论：

| # | 附带判定 | 判据 | 为什么必须有 |
|---|---|---|---|
| 8b | 本次提交里**平台自家 CI** 的 check-run 注解数 | 全部为 0 | 弃用警告修没修好，只能看**新一次**运行 —— 历史运行的注解是只读快照，平台不会重算。**必须只算平台自家 CI**：同一个提交上还挂着别的来源的检查（依赖更新机器人一开 PR 就有一个），一起算就是把别人的注解算到本次头上 |
| 9b | `/releases/latest` 是否落在**最高版本** tag | 一致 | 「最新」不等于「最后推送的那个」；**回填历史 Release 最容易把它抢走**，而 `/releases/latest` 正是给别人下载用的 |

**再加一条**：凭据残留复查（见第五节）—— 它读**全部**配置与对象库内容，不做长度截断。

> 只校验「有没有资产」是不够的：必须按**期望的文件名**去找那一个，
> 顺带确认它不是草稿、不是预发布。只取列表里第一个，等于把发布物交给了排序。

**第 3 项要在推送前先取好基线**，否则推送后无从比较：

```bash
git ls-remote --tags <仓库URL> > "<基线文件>"      # 推送前
```

没有基线时，退而用「远端全部 tag 是否都能在本地找到同名同 sha」做替代判据，
并在结论里**写明这是替代判据**，不要含糊成「历史未变」。

## 二、Git 对象指纹：唯一的跨平台比对基准

**不要比工作区文件的裸哈希，也不要比 zip 的哈希。** 比的是 Git 自己的对象指纹 ——
它与平台、行尾、时区全部无关，也正是 API 返回值所用的口径：

```python
import hashlib

def blob_sha(data: bytes) -> str:
    """与 `git hash-object` / GitHub trees API 的 blob sha 同口径。"""
    return hashlib.sha1(b"blob %d\0" % len(data) + data).hexdigest()
```

注意对象头里的分隔符是**空字节 `\0`**，不是普通的空字符串。

**为什么不比 zip 的整文件哈希**：zip 的条目时间戳取**构建机器所在时区的时间**，
同一个 tag 在 UTC 与 GMT+8 打出的容器字节不同（差异数 = 条目数 × 2）。
把断言打在容器哈希上，会得到一个**随机变红**的流水线。
对外能承诺的是「**逐文件内容相同**」，不是「逐字节相同」。

> **口径要写准，别写成「不可复现」。** 同一构建环境里，同一个 tag 前后两次构建
> （实测间隔几分钟）产出的 zip **digest 完全相同**。准确说法是：
> **同一环境可复现，跨时区不可复现**。前者是能力，后者才是那条要避开的坑。

## 三、读线上状态：端点与判读

公开仓库的读接口**免认证**即可访问，这是回验最省事的一条路。

| 要读什么 | 端点 |
|---|---|
| 全部 ref（分支 + tag）与 sha | `git ls-remote <仓库URL>`（不需要 API） |
| 某个提交的树（递归、含每个 blob 的 sha） | `GET /repos/{owner}/{repo}/git/trees/{sha}?recursive=1` |
| tag 列表 | `GET /repos/{owner}/{repo}/tags?per_page=100` |
| 最近的运行 | `GET /repos/{owner}/{repo}/actions/runs?per_page=<n>` |
| 某提交的检查项与**注解数** | `GET /repos/{owner}/{repo}/commits/{sha}/check-runs` |
| 最新的 Release | `GET /repos/{owner}/{repo}/releases/latest` |
| 全部 Release | `GET /repos/{owner}/{repo}/releases?per_page=100` |
| 下载发布资产 | 资产对象的 `browser_download_url` |

三条判读纪律：

- **`annotations_count` 是判断「警告还在不在」的快捷口径**：
  逐个 check run 看 `output.annotations_count` 是否为 0，比翻注解列表更快更不容易漏。
- **`/actions/jobs/{id}/logs` 需要管理员权限**，公开仓库也不例外 ——
  别在这上面白费时间，改用 check-runs 与 annotations。
- **读接口优先用会做服务端抓取的工具**（如带网页抓取能力的工具），
  它绕开了执行环境网络层的各种限制。**只有要下载二进制资产**时，
  才改用 HTTP 客户端（那一步绕不开）。
  ⚠️ **但它给不了精确字节**：服务端抓取拿回的是渲染后的文本，
  **不能用来算哈希、也不能用来做「逐字节相同」的断言**。
  凡是需要精确字节的比对（资产内容、blob 指纹），必须走能拿到原始响应的那条路。

## 四、三类会「骗过你」的陷阱

三类都实测踩过，共同特征是**报警内容看起来比实际严重得多**。

### 陷阱 1：在不含 `.git` 的目录里跑 `git ls-tree` ⇒ 取到空集

**归档快照按规范不含 `.git`。** 在归档目录里跑 `git ls-tree`，拿到的是**空集**，
于是「差异数」恰好等于远端文件总数 —— **看起来像历史被整个破坏了**，其实只是取数取空了。

**通用判据：差异数恰好等于待比文件总数时，先怀疑自己取到了空集，
而不是先怀疑内容坏了。**

**修法**：改用第一节的**手算 Git 对象指纹**，不依赖工作区里有没有 `.git`。
**并且**：断言里同时打印**两侧集合大小** —— 空集一眼可见。

### 陷阱 2：目录比对只报「不一致」而不分栏 ⇒ 掩盖了路径写错

归档目录常常是**嵌套两层**（`history/<tag>/<name>-<主>-<次>/`，
同层还放着该版的 zip 与说明文件）。若把比对根直接指向外层，
会一次性报出「全部归档都不一致」。

**救命的设计**：目录 vs 目录的比对**永远分开报两栏**：

- **各自独有的路径**（谁多了什么、谁少了什么）
- **同名但内容不同的路径**

第二栏为空时，就能一眼判定是**路径前缀写错了**，内容其实分毫不差。
用脚本回验时，请照这个格式输出。

### 陷阱 3：**检查命令自己**造出的假阴性

前两个是「数据取错了」，这一个更隐蔽：**数据是对的，错的是比对的方式与工具本身。**
它最危险之处在于，结论看起来像一个**严重的事实**（「历史被破坏了」「HEAD 与 tag 不符」），
于是人会去查一个根本不存在的问题 —— 甚至**放弃一条其实走得通的方案**。

| 形态 | 现象 | 根因 | 修法 |
|---|---|---|---|
| **路径分隔符未归一化** | 从两处来源取同一个路径做相等比较，永远不等 | 一处是 `\`、一处是 `/` | 比较前统一走 `normcase(normpath(...))` |
| **shell 吃掉转义符** | `git rev-parse <tag>^{commit}` 被吃成 `{commit}`，报「HEAD ≠ tag」 | 某些 shell（如 cmd）里 `^` 是转义符 | 换不会歧义的取法（`git rev-list -n 1 <tag>`），或把命令写进脚本文件 |
| **集合比较没剥解引用后缀** | 报「tag 集合有差异」，而差异数**恰好等于 tag 总数** | 带注释的 tag 在远端 ref 列表里**成对出现**（多出一行解引用记录），本地只列干净名字 | 比较前剥掉那个后缀，别把行数差当成内容差 |
| **取数没按对象限定** | 报「最新一条 run 不是本次提交」或「本次提交有注解」 | 有机器人开 PR 时，最新 run 与附加的检查属于**别的提交** | 按本次提交的 sha 取数；注解只算平台自家 CI |
| **管道吃掉退出码** | 空输出 + `exit 0`，看着像「仓库存在且为空」 | `关键命令 \| head` 之后取到的 `$?` 是 **`head` 的**退出码，不是关键命令的 | 关键命令**不接管道**：先把输出落盘，再单独读 |

**通用判据（与前两个陷阱同源）：**
**凡是否定式结论 —— 「不存在」「空集」「全不一致」「两者不相等」——
先怀疑取数方式与比对工具，再怀疑数据本身。**
以及：**凡「差异数恰好等于某个总数」，先怀疑取数范围错了**（取到空集、多取了一类对象）。

信号是**严重程度不匹配**：报出来的「罪名」远大于可能的原因。
不匹配就是先停下来自查的理由。

## 五、凭据残留复查

```bash
grep -i -E "<令牌前缀>|x-access-token|@github" .git/config
git config --list --show-origin | grep -i -E "credential|token"
ls -la ~/.git-credentials 2>/dev/null
grep -r -l "<令牌前缀>" .git
```

四项都应为空。**这一步是回验的一部分，不是可选项** ——
凭据留在配置里，比发布物出错更难被发现。

## 六、「跳过」不等于「通过」

回验脚本在**离线 / 缺权限 / 目标不存在**时会跳过某些项。三条纪律：

1. **跳过必须显式打印**，并在汇总里单独计数 —— 不能让它静静地从「失败数 0」里蒙混过去。
2. **只要有一项被跳过，结论就不能写「全部通过」**，只能写「N 项通过、M 项跳过（原因）」。
3. **凡是「已验证 X」的措辞，都要能指回具体哪一行证明了 X。**
   校验步骤若因为可选依赖缺失而返回了占位文案，**那不是通过** —— 那是**没执行**。
   缺依赖时优先**换标准库实现**，而不是降级为空值。

同理，任何**软失败**（异常被吞、返回兜底值）都不算通过。
