## 一、令牌选型与权限矩阵

| 目的 | classic（个人访问令牌） | 细粒度令牌 |
|---|---|---|
| 读代码 / 读 tag | `repo`（公开仓库读甚至不需要） | `Contents: Read` |
| 推代码 / 推 tag | `repo` | `Contents: Read and write` |
| **推 `.github/workflows/` 下的文件** | **`workflow`** | **`Workflows: Read and write`** |
| 建 Release + 传资产 | `repo` 已含 `Contents: write` | `Contents: Read and write` |
| 读 / 发 Packages | `write:packages` / `read:packages` | 同名，缺了 API 一律 `403` |

- **只要这一轮改过或新增过 `.github/workflows/` 下的任何文件，就必须带 `workflow`。**
  classic 的 `repo` **不含**它，这是最容易漏的一项。
- 细粒度令牌还要注意**仓库范围**：它默认只对选中的仓库生效，
  「仓库建好了却推不上去」有时是范围没勾。
- 令牌本身有**有效期**。长任务跨天失败时，先想想是不是它过期了。

## 二、「一半成功」是缺权限的典型症状

缺 `workflow` 权限时的报错原文：

```
refusing to allow a Personal Access Token to create or update workflow
'.github/workflows/validate.yml' without 'workflow' scope
```

**为什么说症状有欺骗性**：推送是按 ref 逐个处理的。
不含工作流文件的**旧 tag 会成功**，含它的新 tag 与主分支**会失败** →
仓库看起来「一半有内容、一半没有」，很容易被误判成网络问题（因为「有点通、有点不通」）。

**判读口诀**：**「部分 ref 成功、部分被拒」时，先查权限，不要先查网络。**
网络问题的表现是「一次都推不上去」，不是「有的行有的不行」。

**补权限不必重贴令牌**：更新已有令牌的勾选项，值不变、即刻生效。

## 三、核实令牌到底带了哪些权限

不要靠记忆认为「我勾了」。**用一次请求读回它的实际权限**：

```bash
curl -sS -D - -o /dev/null -H "Authorization: Bearer <TOK>" https://api.github.com/user
```

响应头里的 **scope 字段**列出的就是该令牌实际拥有的权限集合 —— 拿它逐项核对
（`repo` 与 `workflow` 是否都在）。这是**唯一的**「我说它带了还是没带」的可核对依据。

同理可用来确认令牌是否还有效：返回 `401` 即已失效（被吊销或过期）。

## 四、凭据最小化：为什么用一次性凭据文件

**推送时把令牌交给 git 的方式，按暴露面从大到小：**

| 方式 | 令牌会出现在哪里 | 评价 |
|---|---|---|
| 写进仓库 remote URL | `.git/config` 里明文常驻 | ❌ 最差，且会被后续命令回显 |
| 命令行里的一次性 URL | 进程参数、shell 历史、日志 | ⚠️ 可用，但会被日志/回显碰到 |
| **一次性凭据文件** | 一个临时文件，用完即删 | ✅ **首选** |
| 系统凭据管理器 | 系统凭据库 | ⚠️ 桌面环境会**弹 GUI 等人**，无人值守时会挂住 |

一次性凭据文件的写法（**三个平台一致**）：

```bash
CRED="$(mktemp)"                       # 临时文件
printf 'https://x-access-token:%s@github.com\n' "$TOK" > "$CRED"
export GIT_TERMINAL_PROMPT=0
git -c credential.helper= -c credential.helper="store --file=$CRED" push origin <ref>
rm -f "$CRED"
```

四个必须知道的细节：

1. **`-c credential.helper=` 是「追加」而不是「覆盖」。**
   单写这一句不会清掉系统里已有的 helper —— 它们仍排在前面、仍会弹窗。
   **必须先插一个空值把列表清空**，再接上自己的文件型 helper（上面两句的顺序即是）。
2. **`GIT_TERMINAL_PROMPT=0` 必配。** 否则在无法输入的环境里会一直等。
3. **自写的超时不要超过调用方的超时。** 内层还没轮到就被整条杀掉，
   会导致**连后续读日志的步骤都执行不到**，把「命令没能交出结果」误读成「推送失败」。
4. ⚠️ **装了图形凭据管理器的机器上，这条路可能整条不生效。**
   实测踩过：即使在命令里插了空值清空列表，**系统级的 helper 选择器与凭据管理器
   仍然排在里面**（它们来自系统级配置，不是仓库级），于是推送报：

   ```
   fatal: could not read Username for 'https://github.com': terminal prompts disabled
   ```

   此时改走**命令行里的一次性认证 URL**：

   ```bash
   git push https://x-access-token:<令牌>@github.com/<owner>/<repo>.git <精确 ref…>
   ```

   令牌只出现在这**一条命令的参数**里，不进 `origin`、不写 `.git/config`；
   推完照样复查四处残留。代价是多一次「令牌进进程列表」的暴露面 ——
   所以它优先用于**一次性**场景，长期用法仍然是凭据文件。

## 五、非交互环境里的「零输出 + 被中断」

**同一个症状有两个成因，必须分开：**

| 成因 | 机制 | 分辨方法 |
|---|---|---|
| 凭据管理器弹 GUI 等人 | 无人在屏幕上点，进程一直挂着，直到被外部超时打断 | `git ls-remote`（免认证）**照样正常返回** ⇒ 别把它当凭据可用的证据 |
| 关键命令被接到可能失败的过滤器上 | 过滤器一报错，管道整体崩掉，**主命令的 stdout 被吞** | 主命令的输出**一个字节都没留下**；而远端状态其实已经变了 |

**共同结论**：**`SIGTERM` + 无输出更像「命令没能把结果交出来」，不等于「命令没执行」。**
下结论前先找旁证 —— 最直接的一条是**看远端 ref 是否真的变了**：

```bash
git ls-remote <仓库URL> | head        # 远端的 ref 与 sha 现在是什么
```

**根治写法**：把关键写操作的输出**先落盘、后单独读**，并且**不要给它接过滤器**。

```bash
timeout <不超过调用方超时> git push <ref> > "<日志文件>" 2>&1
# 然后单独读日志文件
```

要打码/改写的，**对落地后的日志文件做**，不要对管道做。

## 六、用完即清：删除与残留复查

**推完立刻删凭据文件，然后逐处复查**（四处都要看，顺序即优先级）：

```bash
# 1) 仓库级配置
grep -i -E "<令牌前缀>|x-access-token|@github" .git/config
# 2) 全局配置
git config --list --show-origin | grep -i -E "credential|token"
# 3) 凭据存储文件（若存在）
ls -la ~/.git-credentials 2>/dev/null
# 4) 仓库对象目录内是否混入过令牌字面量
grep -r -l "<令牌前缀>" .git
```

四项都应为空。

⚠️ **「删掉令牌」这个动作要覆盖所有生成过它的脚本，不只是主流程那个。**
实测踩过：主流程规规矩矩删了临时文件，另一支**诊断脚本**又创建了一个却忘了删，
事后复查时才发现它还在盘上。⇒ 收尾时按「哪些地方写过凭据文件」逐个过一遍，
并**在盘上搜一次**，而不是只在脑子里过一遍。

**吊销与失效是两回事**：补权限用更新（值不变）；**吊销后不可恢复**。
在 GitHub 的 classic token 页面上，那个按钮叫 **`Delete`**，**不叫 Revoke** ——
提醒使用者时用词要准，否则他会找不到。

## 七、CI 里的令牌是另一回事

- 工作流里用平台**自动注入的令牌**（`secrets.GITHUB_TOKEN`），不要往仓库里塞个人令牌。
- 它通过**工作流的 `permissions:` 声明**获得权限，所以：
  - 只读的校验工作流写 `contents: read`；
  - 需要建 Release 的工作流单独一个文件、写 `contents: write`。
  **两个工作流分开写，就是为了不让例行检查带上多余的写权限。**
- 需要跨仓库操作时，才考虑单独的密钥；那类密钥同样要遵守「用完即吊销」。

## 八、安全义务清单

- [ ] 使用者贴了**密码**：明确告知它**未被使用、未写入任何文件**，并建议尽快更换
      （平台自 2021-08 起已停用密码认证，密码对推送无效）。
- [ ] 使用者贴了**令牌**：注意它已进入对话记录 —— 按**已泄露**处理，用完即吊销并提醒。
- [ ] 令牌**从未**写进 `.git/config`、URL、仓库里的任何文件。
- [ ] 凭据文件已删除，四处残留复查为空。
- [ ] **每个**生成过凭据文件的脚本都过了一遍，盘上搜过一次，临时文件全部删除。
- [ ] 把「这个令牌现在还有效吗」「它带了哪些权限」的核实方式**写下来**，
      而不是靠回忆 —— 下一次换机器时，这是最先要确认的两件事。

## 九、两条等价的执行路径：纯 git 与官方命令行工具

到远端的写操作有两条路，**权限要求完全一致**，差别在「要写多少取数代码」：

| 维度 | 纯 git + 平台 REST 接口 | 官方命令行工具（如 `gh`） |
|---|---|---|
| 依赖 | 只需 git 与标准库 HTTP 客户端 | 需要单独安装那个工具 |
| 建仓 / 建 Release / 看与重跑流水线 | 每件事都要自己拼请求、自己处理分页 | 一条子命令，输出结构化 |
| 判据的细粒度 | 高 —— 能看到每个字段 | 中 —— 它替你做了取舍 |
| 认证 | 一次性凭据文件（本文件第四节） | 工具自己的登录态，或从环境变量读令牌 |
| 适用 | 无外部依赖的场合、CI 里、要精确取数时 | 交互式排障、想少写代码时 |

**做法是「先探测再分支」，不要假定某个工具存在**：

```bash
command -v gh >/dev/null 2>&1 && echo "有" || echo "没有"
```

- 有 → 可以用它做建仓、建 / 查 Release、看与重跑工作流；
- 没有 → 走纯 git 路径，**不要为了它去装东西**（安装本身可能又撞上通路问题）。

⚠️ **两条路不要混着用来做「推送」这一步。** 用工具推送时，它的提交时间与
tag 处理方式可能与本地重构出来的历史不一致；**历史保真度最高的仍然是
从本地直接 `git push` 精确 ref**（见主文件阶段 6 与网络诊断一篇的「三类都不行」）。

⚠️ **工具报的「成功」也要回验。** 它把多步操作包成一条命令，失败时可能只给一行摘要；
主文件阶段 9 的九项回验**与用哪条路无关**，照跑。

> 另一件事：工具与网页端的「授权」**不等于**当前会话里就能用。
> 授权完成后往往需要**新开一个会话**，权限才会生效 —— 别在同一个会话里反复重试。
