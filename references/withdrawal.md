# 撤回与作废：发错了怎么办

整套流程都在讲「怎么正确地推上去」。这一篇讲**推错了怎么办**。

它必须存在，因为本技能的另一条纪律是**「发出去就锁死」**（见主文件阶段 8）。
一旦承认锁死，撤回就是唯一的补救手段；而「唯一的手段」如果没人写清楚，
出事那天就只能临场发明 —— 那通常意味着删掉一个别人正在依赖的东西。

## 一、一句话定义

**撤回 = 下架 + 公告。**

它**不是**「把东西收回来」。已经下载、已经依赖、已经在生产里跑的人，你追不回来。
它改变的只有两件事：**新用户还能不能拿到**，以及**已经拿到的人知不知情**。

> 类比：卖出去的书，读者家里有。你追不到人家家里去拿回来（= 删除），
> 但可以从书架上撤下来（新读者买不到），再在公告栏贴一张纸（已买的人知道该换）。
> 撤回做的是后两件事。

## 二、为什么「删除」近乎禁忌

这不是约定俗成的礼貌，是一次真实事故换来的规则。

**2016 年 3 月**：一位开发者把自己发布在 npm 上的、只有十来行的小模块删掉了。
结果大量项目的构建当场失败 —— 它们的依赖树深处用到了它，几小时内整个 JavaScript
生态连锁停摆。此后 npm 收紧删除政策，其他注册表也跟着明确了限制。

教训：**你删掉的不是「你的东西」，是别人依赖清单里的一个节点。**

政策由此定形：

> **下架（yank）几乎总是对的，删除（delete）几乎总是错的。**

## 三、「下架」到底做了什么

以 Python 生态的官方定义（PEP 592）为例，它的精确语义是：

| 用户怎么装 | 结果 |
|---|---|
| 不指定版本（`install 包名`） | **跳过**被下架的版本，自动选可用的 |
| 明确钉住（`install 包名==2.28.0`） | **照样装得上**，只多一行提示 |

后一条是**故意设计的**：生态把「钉住某个版本」看作一种郑重承诺 ——
用户公开声明「我就要这一版」，任何人不该让他的构建突然坏掉。

⇒ 由此得到一条必须记住的结论：

> **下架不是修复，它只是阻止新的踩坑。**
> 已经装上有问题那个版本的人不会自动获救；**仍然需要漏洞扫描工具**，
> 才能发现「当初钉住的版本，现在不安全了」。

## 四、三种手段的强度对照

| 手段 | 新用户（默认安装） | 老用户（已钉住该版本） | 定位 |
|---|---|---|---|
| **删除** | 构建直接失败 | 构建直接失败 | 近乎禁忌，只在法律要求或恶意投毒时由平台执行 |
| **下架** | 自动跳到修好的版本 | 照常装上，附提示 | **默认选择** |
| **标记弃用** | 照常装上，附警告 | 照常装上，附警告 | 最弱；不阻止，只提醒 |

各生态的对应入口（判据相同，命令不同）：

| 生态 | 手段 | 入口 |
|---|---|---|
| PyPI | `yank` | 项目页 → 版本 → Options → Yank；或 `twine yank` |
| crates.io | `yank` | `cargo yank --version X.Y.Z` |
| RubyGems | `yank` | `gem yank -v X.Y.Z` |
| npm | 发布 72 小时内且无人依赖可 `unpublish`（**不推荐**），之后只能 `deprecate` | `npm deprecate 包名@版本 "原因"` |
| Maven Central | **几乎不可能回滚** | 唯一方案：发新的修复版本 |
| **平台上的 Release**（本项目） | 改说明 / 改 Latest 标记 / 删 Release | 见下一节 |

> **不要试图删除已发布的版本号并重用。** 主流平台都会**永久烧掉**那个号
> （PyPI 明确如此），或者干脆不允许。正确做法永远是**顺延号位**。

## 五、本项目能做的那三个动作

本项目不是包管理器上的包，没有 `yank` 命令。可用的只有三个动作。

### 动作 1 · 改说明 + 抢回 Latest

编辑那个坏版本的 Release：

- 标题加醒目前缀，例如 `[已作废 / DO NOT USE] 3.0`；
- 说明顶端写三段：**问题是什么** / **影响谁** / **该改用哪个版本**；
- 如果它被标成了 `Latest`，**把标记移走**。

⚠️ **`Latest` 是自动判定的**（按日期与版本）。坏版本若是最近发的，
它会**自动成为仓库页上的门面** —— 新来的人第一眼看到的就是它。
**把 Latest 抢回来，通常只能靠再发一个版本**（也可以手动把标记指到另一个 Release）。

### 动作 2 · 公告

按受众选渠道，从上到下覆盖：

- **Release 说明本身**（已经点进来的人会看到）；
- **README 顶部**一行显著提示（新来的人会看到）；
- **安全公告** —— 涉及漏洞时用这个，它会进依赖扫描的数据库；
- 必要时把一条 issue 置顶。

### 动作 3 · 发修好的新版

**这是唯一真正解决问题的动作**，也是把 Latest 抢回来的手段。
按号位纪律**顺延**，绝不覆盖已发布的号位。

## 六、门槛：什么情况才必须撤回

### 6.1 判据

> **发布物里带出了不该公开的东西 —— 泄露了用户个人信息、工程信息、项目信息。**

这句话是好判据，但**必须先拆成三类**，因为三类的严重程度与补救手段完全不同。
混在一起会得到一个「什么都算严重」的假门槛，而**假门槛比没门槛更危险**：
没门槛时你知道自己没保障，有假门槛时你以为有保障。

### 6.2 三类信息，三种处置

| 类型 | 具体是什么 | 处置 | 为什么 |
|---|---|---|---|
| **A · 凭据类** | 令牌、私钥、密码、数据库连接串、云服务密钥 | **先轮换，再撤回，再公告** | 见 6.3，顺序不能反 |
| **B · 个人信息类** | 真实姓名、手机号、邮箱、身份证件号、**绝对路径里的系统用户名**、内网地址与主机名、同事或客户姓名 | **撤回 + 重打** | 「已经下载的人手里那一份」会害他 |
| **C · 工程 / 项目信息类** | 私有仓库名、未公开的产品计划、内部架构图、客户名单、内部定价 | 涉竞争或合同 ⇒ **撤回**；不涉 ⇒ **仅顺延新版** | 由你按「被人看到会不会有实际损失」判 |

> **B 类里最容易被忽略的是「绝对路径里的系统用户名」。** 它看起来无害，
> 但形如 `<盘符>:\<用户目录>\<真实用户名>\…` 的路径**同时泄露了系统用户名**，
> 而系统用户名往往就是真名或常用网名 —— 这是最常被无意带出去的一类。
> 本技能的发布前隐私扫描（第八节）专门抓它。

### 6.3 ⚠️ 凭据类：次序不能反

**第一动作不是撤回，是轮换凭据。**

理由是平台上的一条硬事实：

> 一旦推到**公开**仓库，就必须假设它**已经被抓走了**，无论你删得多快。
> 平台自己的说法就是：敏感数据推到公开仓库后，**撤销或轮换该凭据才是第一动作**。

因为公开仓库的暴露面远不止「有人点进来看」：

- **永久存档**：平台每小时把全部公开事件存档一份，删掉源仓库也去不掉存档；
- **搜索引擎与代码搜索站**会持续爬取并留索引；
- 别人 fork、clone 出去的副本，你无法回收。

所以正确次序是：

```
① 轮换 / 吊销凭据   ← 止损，立刻做，与撤回并行
② 撤回 + 改说明      ← 让新来的人不再下载
③ 公告              ← 让已经拿到的人知道
④ 顺延发修好的新版
```

**为什么撤回不能替代轮换**：撤回需要时间（改说明、等索引更新），
而凭据在泄露的那一秒就已经失效了。**轮换是自保，撤回是给别人看。**

### 6.4 判据可以简化成一句话

> **问「已经下载的人手里那一份，会不会害他」。**
> 不会 ⇒ 发补丁版本；会 ⇒ 撤回。

这句话把「凭据泄露」与「文档写错」自动分到了两边，不需要记表格。

### 6.5 逐行判定

| 情形 | 常见做法 | 建议判定 |
|---|---|---|
| 凭据 / 密钥被打进发布物 | 撤回 + **立刻轮换** | ✅ **撤回**（且**先轮换**，见 6.3） |
| 个人信息被打进发布物 | 撤回 + 重打 | ✅ **撤回** |
| 工程 / 项目内部信息被打进发布物 | 看敏感程度 | ✅ 涉竞争或合同则**撤回**；否则顺延新版 |
| 存在可利用的安全漏洞 | 撤回 + 发安全公告 | ✅ **撤回** + 安全公告 |
| 会损坏、删除或污染用户数据 | 撤回 | ✅ **撤回** |
| 完全装不上 / 一启动就崩 | 撤回 | ✅ **撤回** |
| 误用了他人代码、或存在许可冲突 | 撤回 | ✅ **撤回** |
| 装得上，但计算结果 / 输出是错的 | 多数**不撤**，发补丁版本 | ⬜ **不撤**，顺延新版 |
| 只在某个特定平台 / 环境坏 | 多数**不撤**，发补丁版本 | ⬜ **不撤**，顺延新版 |
| 文档写错、说明有误 | **不撤**，在下一版说明里更正 | ⬜ **不撤** |

### 6.6 两个量

| 待定项 | 说明 | 建议值 |
|---|---|---|
| 发现问题后多久内必须公告 | 越短代价越大，但拖着会覆盖更多用户 | **A 类：立刻（小时级）**；**B / C 类：24 小时内** |
| 谁有权决定撤回 | 单人项目通常就是自己；留一行是为了将来 | 仓库所有者（单人项目即本人） |

> 这两个都是**风险偏好**，不是技术判据 —— 要给具体数字，理由只有一个：
> 没写下来的默认值就是「拖着」。数值可以随时改，**空白不行**。

## 七、什么情况不需要撤回

避免把撤回当成万能动作 —— **滥用会让它失去信号价值**。
（同一条道理见长期维护一篇：一条永远亮着的警告会训练人忽略警告。）

- **功能 bug**：不影响安全、不坏数据 ⇒ 发补丁版本即可；
- **性能不理想**：同上；
- **文档错误**：改下一次的说明，不必作废；
- **只在罕见环境下坏**：多数发补丁版本，并记录已知问题。

## 八、把门槛挡在发布之前：三道闸

### 8.1 为什么「事后撤回」治不了本

回到 6.3 的那条硬事实：**一旦公开，就假设已经被抓走了。**

⇒ 对「泄露用户信息」这一类，撤回的**实际能力非常有限**：
它能阻止的是「之后来的人」，无法阻止「已经发生的事」。
**撤回到位了，泄露也已经成立了。**

所以对这类风险，正确的姿态不是「出事之后撤得快」，而是**让它出不去**。
撤回门槛该有，但它是**最后一道**，不是主防线。

### 8.2 三道闸，从便宜到贵

| # | 闸门 | 位置 | 成本 | 挡住什么 |
|---|---|---|---|---|
| 1 | **发布前隐私扫描**（在结构自检脚本里） | 本地，提交前 | 一次性写规则 | 令牌与密钥形态、私钥块、真实邮箱、手机号、绝对路径、内网地址与主机名 |
| 2 | **平台的推送保护**（Secret Scanning + Push Protection） | 远端，推送瞬间 | **零**（公开仓库免费） | 已知格式的凭据 —— 各平台令牌、云厂商密钥等 |
| 3 | **发布前人工清单**（见主文件检查清单末段） | 本地，建 tag 前 | 几分钟 | 闸门 1、2 看不懂的语义类信息（内部计划、客户名单） |

> 闸门 2 的性价比最高：它**不需要写任何代码**，推送的那一刻直接拒绝含凭据的推送。
> 但它默认**不一定开着** —— 公开仓库要去仓库设置里确认一次。
> 这件事属于「配好之后就不用再想」，所以属于**现在就该做掉**的一类。

### 8.3 闸门 1 的规则与它的两条纪律

规则清单（命中即 FAIL，不是警告）：

- **令牌与密钥形态**：各平台的固定前缀后跟足够长的字符；
- **私钥块**：PEM 头尾标记（以连字符框住的那种）；
- **真实邮箱**：排除官方的匿址邮箱，以及 RFC 2606 / 6761 保留给文档的域名与顶级域；
- **手机号形态**：中国大陆 11 位、特定号段，且两侧不再挨着字母数字；
- **内网主机名**：以 `.internal` / `.local` 结尾的名字（**只扫文档与配置**）；
- **绝对路径与 IP 字面量**：这两条已有独立规则覆盖，不重复。

两条纪律：

1. **检查某种字面量的代码，自身不得含有该字面量的完整形态。** 规则常量一律
   **拼接构造** —— 否则将来一次全局替换会把检查器改坏，而它**静默打印「通过」**。
2. **宁可列白名单，也不要模糊判据。** 白名单窄了会天天误报，宽了才敢让它一直开着；
   **规则太爱误报就会被关掉**，那等于从来没有这条规则。
   （同源教训：源码里「对象点属性」的写法与内网主机名长得一模一样 ⇒ 这条规则不扫源码。）

## 九、与不可变发布的关系

开启不可变发布之后，**Release 的资产与对应的 tag 被锁定**：资产改不了也删不掉，
tag 不能被重指。但它**只锁这两样**：

| 对象 | 不可变发布开启后 |
|---|---|
| 资产文件 | **锁** —— 不能改、不能删、不能补传 |
| tag 指向 | **锁** —— 不能移动；删掉 Release 后才可删 tag，但**tag 名不可复用** |
| 标题 / 发布说明 | **可改** |
| 预发布 / Latest 标记 | **可改** |

⇒ 结论：它挡的是「有人偷换你的发布物」这类**供应链攻击**，
**完全不挡**撤回流程要用的那几个动作。**可以直接开**。

但它带来一条**顺序要求**：不可变发布**只保护开启之后创建的 Release**，不追溯。
所以发布流程必须是 ——

```
先建草稿  →  传完所有资产  →  再点发布
```

否则发布后发现漏传一个文件，就**永远补不上**（只能删掉整个 Release 重发，
而 tag 名又不能复用 ⇒ 只能顺延号位）。
资产由 `git archive` 从 tag **现算**的项目天然是「一次算完、一次传完」，
不存在分批补传，所以这条代价接近于零。
