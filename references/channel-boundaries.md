# 两个分发渠道，两套规则

同一批文件，可能要被交给**两个完全不同的地方**：一个 Git 托管平台的 Release，
和一个技能平台的「上传」入口。它们的规矩不一样，而且**都硬**（各自都有平台级的
报错原文作依据）。不把这件事说清，就会出现「同一个问题、两个技能各说各话」。

## 一、冲突是怎么产生的

两条规则单独看都对：

- **规则甲**：版本号写 `主.次` 两级。依据是本项目自己的纪律，且三处必须一致。
- **规则乙**：版本号必须是三段式 SemVer。依据是**平台自己的报错原文**
  （「版本号格式不合法，请使用 SemVer 2.0.0 格式（如 1.0.0）」）。

它们看起来互相打脸 —— 一个说两段、一个说三段。但真相是：

> **它们说的不是同一个东西。** 甲说的是「这个 Git 仓库的 tag 叫什么」，
> 乙说的是「上传到那个平台时，表头里的 `version` 字段填什么」。

所以这不是「同一个问题的两种解法」，**而是两个问题恰好共用了「版本号」这个词**。
两者的修法方向也相反：甲要的是「一个号位只指向一份内容，改了必须顺延」，
乙要的是「**每次重传前必须递增**」—— 后者是平台为了区分上传批次而定的，
和内容有没有变无关。

同类现象还有「描述字段多长」：本地装载器根本不校验长度，
而平台会直接拒绝上传。**只有平台会因此报错，所以上限以平台为准。**

## 二、两个渠道各是什么

| | **渠道 A：发布到 Git 托管平台** | **渠道 B：上传到技能平台** |
|---|---|---|
| 交付形态 | 仓库 + tag + Release（附一个 zip 资产） | 一个 zip，经平台校验后上架 |
| 版本号的权威来源 | **git tag** | **表头里的 `version` 字段** |
| 版本号形态 | 两段式 `主.次` | 三段式 SemVer `主.次.修订` |
| 表头字段 | `name` / `description` / `license` / `metadata.version` | 固定七字段，其中三个是描述字段 |
| 描述字段上限 | 不校验（但要为渠道 B 留余量） | **每个描述字段 1000 字符** |
| 同号位能否重发 | 可以，但会破坏「一个号位一份内容」 | **不能**，会被平台拒；必须递增 |
| 打包方式 | 从 tag 现算（保证发布物可由 tag 重现） | 手工打包，首层必须是技能目录名 |
| 谁能给出最终判决 | 本项目的回验脚本 + CI，可离线复算 | **只有平台能判**，本地只能预检 |

## 三、逐项对照

| 项 | 渠道 A | 渠道 B | 冲突时以谁为准 |
|---|---|---|---|
| 版本号形态 | 两段式 | 三段式 | **分渠道，各按各的** |
| 描述长度 | 无硬约束 | ≤ 1000 | **渠道 B**（只有它会拒） |
| zip 首层目录 | `{仓库名}/`（`git archive --prefix`） | `{技能目录名}/` | **渠道 B**（校验更严） |
| 版本号写在哪个键 | `metadata.version` | 顶层 `version` | **分渠道** |
| 「改了能不能就地改」 | 能（强推），但会毁掉可验证性 | 能，但必须换号位 | **渠道 A 更严** |

> 注意最后一行：**两个渠道的严格程度不是一边倒**。
> 「同一号位只能有一份内容」这条在渠道 A 上更严，所以在渠道 A 里我们才需要
> 「顺延新号位」的纪律；而渠道 B 只关心号位有没有变大。

## 四、怎么判：先问「这个包要交给谁」

动手之前先回答一个问题，**它决定后面用哪套规则**：

1. **只发布到 Git 托管平台** ⇒ 走渠道 A。版本号两段式，不用管三段式的要求。
2. **只上传到技能平台** ⇒ 走渠道 B。三段式 SemVer，七字段，描述卡在 1000 以内。
3. **两个都要** ⇒ 两套都写，并且**显式绑定两者**（例如 tag `3.1` ↔ 平台版本 `3.1.0`），
   把映射规则写进文档。**绝不要让两个编号各自漂移** —— 那正是「一堆号位对不上」的成因。

自检脚本按**表头形态**自动识别属于哪个渠道（顶层有 `version` 且带 `display_name` /
`description_zh` / `description_en` ⇒ 渠道 B），也可以用参数强制指定。
拿一个渠道的规则去判另一个渠道的包，只会得到一个**假 FAIL**。

## 五、裁决：哪些问题归谁

同一台机器上装了多个技能时，同一个问题可能被两个技能各答一遍。判据是
**「谁对这个问题的后果负责」**：

| 问题 | 归谁 | 为什么 |
|---|---|---|
| 描述字段上限是多少 | 渠道 B 的规范 | 只有平台会因为超限而拒绝 |
| 版本号形态 | **分渠道**，没有唯一答案 | 两个注册表各自的规矩，不存在「哪个更对」 |
| 包内能不能出现环境专属值 | 本技能的可移植性规则 | 换机器就失效，与渠道无关 |
| 网络不通怎么分层定位 | 专管网络诊断的技能 | 本技能只给判据阶梯，不重复它的解法清单 |
| 建 Release / 看运行记录 | 命令行工具那条路径 | 取数方式，不是判据 |

**通用做法**：一处定义、别处引用。同一个数字不要在两个地方各写一遍 ——
两边一旦漂移，模型会随机挑一个，使用者无从判断。

## 六、三种 zip 命名不要混

这是最容易造成「号位对不上」的地方之一：同一个版本会同时存在三种 zip，
**它们的命名词法不同，而且都有理由**。

| zip | 命名 | 给谁 | 为什么是这个形态 |
|---|---|---|---|
| 交付整包 | `{技能名}-{主}-{次}.zip` | 人 | 一看就知道是第几版；点号在目录名里非法，所以用连字符 |
| Release 资产 | `{技能名}.zip` | 部署 | 资产名要稳定，解压后目录名必须等于表头里的 `name` |
| 平台上传包 | `{技能名}_v{主}.{次}.{修订}.zip` | 平台 | 平台要区分上传批次，所以带三段式版本号 |

**不要试图把它们统一成一种写法** —— 它们的读者不同，统一只会让某一方不方便。
要做的是**在文档里把三者列清楚**，这样看到任意一个都知道它是干什么的。
